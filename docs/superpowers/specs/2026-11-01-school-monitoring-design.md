# تخصيص إدارة المدارس ومتابعة الحصص — المرحلة الأولى

التاريخ: 2026-11-01

الحالة: اعتمد المستخدم التصميم وطلب بدء التعديل في 2026-11-01. بدأ التنفيذ ببيانات ولي الأمر ونموذج أهداف التعلم؛ تفاصيل التنفيذ وحدود التحقق في `docs/school-monitoring-pilot.md`.

## الغرض

تحتاج المؤسسة إلى إدارة مدارسها وتسجيل الطلاب، والتواصل مع أولياء الأمور، ومتابعة تنفيذ حصص المعلمين، وتسجيل تحقق أهداف التعلم لكل طالب. المشكلة الحالية أن بعض المعلمين يستلمون رواتب دون الالتزام بالتدريس. يُراد إبقاء البصمة وإضافة صور للحصص لمساندة مراجعة المؤسسة.

## ما أكده المستخدم

- ربط الطالب بولي أمر ورقم هاتف أساسي مهم وإلزامي، ورقم ثانوي إن وجد.
- يلتقط الأستاذ صورة عند بداية الحصة وصورة عند نهايتها.
- تظهر في كل صورة الأستاذ مع الطلاب داخل الفصل، بحسب توضيح المستخدم.
- يستمر استخدام البصمة؛ الصور إضافة إلى المتابعة الحالية.
- لكل مرحلة أهداف تعلم، ويسجل الأستاذ تحققها لكل طالب؛ مثال المستخدم: هل يستطيع الطالب كتابة اسمه عند نهاية التمهيدي أو الصف الأول؟
- يبدأ العمل بهذه الاحتياجات وتضاف التفاصيل بعد الرجوع إلى المؤسسة.

## البدائل والاختيار المقترح

| البديل | الملاءمة | الأثر |

| OpenEMIS كأساس مع تخصيص متابعة الحصص | إدارة المدارس والطلاب والمعلمين وأولياء الأمور، مع وجود تقييم الكفاءات والجداول والحضور | الخيار الموصى به؛ يعيد استخدام الوظائف الموجودة ويضيف التوثيق المطلوب |

| تشغيل النظامين وربطهما | مناسب إذا ظهرت حاجة مستقلة لتعلم إلكتروني متكامل إلى جانب الإدارة المدرسية | يؤجل إلى ظهور حاجة واضحة؛ يزيد إدارة الحسابات والبيانات والتكامل الآن |

التوصية من مراجعة الاحتياج والكود: OpenEMIS، واعتمد المستخدم بدء العمل بناءً عليها. وُجد في النسخة المحلية ملف `version` بقيمة `5.4.1` رغم تسمية المجلد `v5.7.0`؛ يلزم التحقق من إصدار التطبيق وقاعدة البيانات الفعليين قبل أي ترقية أو ترحيل.

## 1. الطالب وولي الأمر

- استخدام سجل ولي الأمر وربطه بالطالب وصلة القرابة الموجودة في النظام.
- حفظ الرقم الأساسي والثانوي ضمن وسائل اتصال ولي الأمر، مع تمييز الأساسي، بدل نسخ أرقامه في سجلات مستقلة لكل ابن.
- الاقتراح: يشترط إكمال التسجيل الجديد وجود ولي أمر مرتبط له رقم أساسي. الرقم الثانوي اختياري.
- عند وجود طلاب مسجلين مسبقًا تنقصهم هذه البيانات، تعرض قائمة لاستكمالها دون حذفهم أو تعطيل الوصول إلى سجلاتهم.
- تطبيق شرط التسجيل في الخادم، مع مراجعة مسارات الواجهة والاستيراد وواجهات API ذات الصلة قبل تعديله؛ لا يكفي تغيير شكل الحقل.
- يعتمد تنسيق الهاتف والتحقق منه على البلد الفعلي؛ لا تفترض هذه المسودة طولًا أو بادئة محددين.

معيار القبول: يتضح ولي الأمر ورقمه الأساسي عند فتح الطالب، ويمكن إضافة رقم ثانوي وربط ولي الأمر نفسه بأكثر من طالب.

## 2. توثيق الحصص

- استخدام إسناد المعلم إلى المدرسة والفصل والمادة والجدول الموجود كأساس لتعريف الحصة.
- إضافة سجل لتوثيق كل حصة مجدولة في تاريخها، مرتبط بالأستاذ والمدرسة والفصل والمادة.
- اقتراح البداية: التصوير من كاميرا الجوال عبر صفحة النظام؛ تحفظ صورة البداية وصورة النهاية منفصلتين مع وقت استلام الخادم لكل منهما.
- يمنع تكرار سجل للحصة نفسها. لا تقبل نهاية قبل تسجيل البداية. لا تعتبر الحصة موثقة عند فقد إحدى الصورتين.
- وقت استلام الخادم يثبت وقت وصول الصورة؛ لا يكفي وحده لإثبات وقت التقاطها أو صحة محتواها. ولا تستطيع قيود المتصفح وحدها منع كل أشكال التحايل.
- يقترح فحص التطابق التام للملفات لتعليم إعادة استخدام الصورة نفسها للمراجعة، دون ادعاء كشف جميع الصور القديمة أو التلاعب.
- حالات المتابعة المقترحة: لم يبدأ التوثيق، بداية فقط، بانتظار المراجعة، معتمد، يحتاج استكمالًا. الصورة الناقصة لا تعني تلقائيًا غيابًا مؤكدًا.
- للمراجع المخول اعتماد التوثيق أو طلب الاستكمال مع سبب. تسجل هوية المراجع والتوقيت وأي تعديل.
- تحفظ الصور في تخزين محمي؛ تحميلها وعرضها يتطلبان صلاحية للمدرسة والسجل، ولا تكون لها روابط عامة.
- تستخدم آلية رفع الملفات الموجودة مع فحص النوع والحجم والمحتوى على الخادم. التصوير بالجوال يتطلب تجربة فعلية عبر HTTPS وصلاحية الكاميرا.
- مدة حفظ الصور وسياسة تصوير الطلاب تحددهما المؤسسة قبل استخدام بيانات حقيقية؛ لا تفترض المسودة حفظًا دائمًا أو نشر الصور لأولياء الأمور.

معيار القبول: يمكن للمراجع استعراض حصص يوم محدد ومعلم محدد، ورؤية حالة كل حصة وصورتيها وتوقيت الاستلام واتخاذ قرار موثق؛ ولا يستطيع مستخدم غير مخول الوصول إلى الصور بتغيير الرابط.

## 3. البصمة

- تبقى سجلات البصمة مستقلة عن صور الحصص؛ حضور الموظف إلى المدرسة وتنفيذ حصة محددة أمران مختلفان.
- لم تثبت المراجعة وجود تكامل جاهز مع جهاز البصمة المستخدم لدى المؤسسة.
- يتحدد الربط بعد معرفة الشركة والموديل والنظام الحالي وعينة تصدير أو وثائق API ومعرف الموظف.
- عند توفر تصدير مناسب، يمكن البدء باستيراد السجلات بدل اشتراط اتصال مباشر بالجهاز.
- لا تنفذ خصومات رواتب تلقائية في المرحلة الأولى؛ يصدر النظام بيانات للمراجعة وفق ما تعتمده المؤسسة.

## 4. أهداف التعلم

- استخدام وحدات Competency ونتائج الطلاب الحالية بدل إنشاء منظومة تقييم موازية.
- تربط الأهداف بالمرحلة أو الصف والفترة التعليمية المناسبة.
- مثال تجريبي: «يكتب اسمه». يقترح سلم: لم يُقيّم، لم يتقن، يتقن بمساعدة، يتقن مستقلًا. هذا السلم اقتراح يحتاج توافقه مع جداول المؤسسة.
- عدم إدخال تقييم يظل غير مقيم ولا يحول إلى رسوب أو عدم إتقان.
- يسجل الأستاذ تقييم الطالب والملاحظة في الفترات المتفق عليها؛ ويعرض تقرير تحقق الأهداف لكل طالب وفصل.
- تؤخذ قائمة الأهداف الحقيقية من جداول المؤسسة؛ المثال ليس منهجًا معتمدًا.

معيار القبول: يمكن إعداد هدف للصف، وتقييم الطلاب عليه، وعرض الطالب الذي أتقن الهدف أو يحتاج متابعة دون خلطه بمن لم يُقيّم.

## الصلاحيات المقترحة

- الأستاذ: حصصه والطلاب المسندون إليه، وتوثيق حصصه وإدخال تقييماتهم.
- مراجع المدرسة: مراجعة توثيق الحصص والتقارير ضمن مدرسته وفق التكليف.
- إدارة المؤسسة: تقارير المدارس المخولة لها.
- لا يضاف حساب لولي الأمر أو إرسال رسائل آليًا لمجرد تسجيل رقم هاتفه؛ ذلك احتياج مستقل إن طلبته المؤسسة.

## ترتيب التنفيذ المقترح

1. التحقق من النسخة المثبتة ومسارات التسجيل والصلاحيات، مع الحفاظ على التعديلات الموجودة في مساحة العمل.
2. تجهيز الطالب وولي الأمر والرقم الأساسي والثانوي باستخدام الوظائف الموجودة، وتطبيق شرط اكتمال التسجيل.
3. تجربة هدف تعلم واحد على بيانات وهمية باستخدام الكفاءات الحالية.
4. إضافة توثيق الحصص والمراجعة بعد تثبيت طريقة الجدولة والتصوير.
5. ربط البصمة عند توفر تفاصيل الجهاز، ثم تجربة المسار كاملًا في مدرسة تجريبية قبل التوسع.

## نقاط تحتاج معلومات من المؤسسة

- توفر الإنترنت والأجهزة أثناء الحصص؛ لا يفترض التصميم أن استقبال الخادم يساوي وقت التصوير عند انقطاع الاتصال.
- نوع جهاز البصمة وطريقة استخراج بياناته.
- من يراجع الصور، وهل يقبل الاستكمال المتأخر وبأي ضوابط؟
- جداول المراحل وأهدافها وسلم تقييمها الفعلي.
- ضوابط التقاط صور الطلاب وصلاحية الاطلاع ومدة الاحتفاظ.

هذه التفاصيل لا تغير إمكان البدء ببيانات ولي الأمر وتجربة الكفاءات؛ لكنها تؤثر في تنفيذ التصوير والربط قبل التشغيل الفعلي.

## أساس التحقق وحدوده

فحصت هذه الوحدات في الكود المحلي: Student.StudentGuardians، User.Contacts، Institution.StaffAttendances، Schedule.ScheduleTimetables، Institution.StudentCompetencies، Institution.InstitutionCompetencyResults. وجودها يؤيد إعادة استخدامها لكنه لا يثبت نجاح المسار على قاعدة البيانات الحالية. لم ينفذ في هذه المرحلة تعديل لكود المنتج أو قاعدة البيانات أو تكامل مع جهاز.
